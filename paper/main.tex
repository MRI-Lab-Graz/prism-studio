\begin{abstract}
Psychological and behavioral studies often combine neuroimaging with
questionnaires, participant metadata, physiological recordings, eye tracking,
and other tabular measurements. The Brain Imaging Data Structure (BIDS)
provides an effective baseline for organizing neuroimaging datasets and
associated behavioral files \citep{gorgolewski2016bids}, but many psychology
workflows still depend on ad hoc spreadsheets, incomplete codebooks, and
lab-specific conventions for instrument metadata, response levels, and
derived scores. BIDS standardizes dataset \emph{structure}; it says little
about the \emph{content} of a behavioral measure, and behavioral research is
open-ended in a way that resists any fixed catalogue of instruments. PRISM
is a local-first, open-source toolkit for converting, validating, and
documenting psychological experiment datasets while remaining compatible
with BIDS. It adds schema-driven metadata for surveys, biometrics,
physiological recordings, eye tracking, and environment/context files
additively, without replacing core BIDS conventions. Its schemas constrain
the shape of an instrument description without enumerating which
instruments exist, so a lab can fully validate a questionnaire PRISM has
never seen, in a language it does not ship, and can extend validation with
its own plugin checks. A validator usable interactively, at the command
line, and in continuous integration makes that contract executable rather
than aspirational, and a guided local-first interface with full
command-line parity addresses the last-mile adoption problem that structure
alone does not solve. We describe the design and present validation
evidence from a seeded, synthetic adversarial test suite that exercises the
pipeline against 59 deliberately hostile inputs.
\end{abstract}

\section{Introduction}

\subsection{What BIDS provides, and what it deliberately leaves open}

The Brain Imaging Data Structure \citep{gorgolewski2016bids} is a community
standard that specifies how a neuroimaging dataset is laid out on disk.
Rather than inventing a database format, BIDS standardizes directory
structure and filenames: measurements live in
\texttt{sub-<label>/ses-<label>/<modality>/} directories, and each file name
is composed of ordered key-value \emph{entities}
(\texttt{sub-}, \texttt{ses-}, \texttt{task-}, \texttt{acq-}, \texttt{run-},
and others) followed by a modality suffix. Every data file may be
accompanied by a JSON \emph{sidecar} of the same basename carrying its
metadata, and sidecars inherit along the directory hierarchy, so shared
parameters can be declared once at the top level. A dataset-level
\texttt{dataset\_description.json} and a tabular
\texttt{participants.tsv} describe the study and its participants.
Crucially, the standard ships with a validator, so ``is this a valid
dataset?'' has a mechanical answer rather than an opinion. This combination
of predictable paths, self-describing sidecars, and automated checking is
what makes BIDS datasets portable between analysis pipelines, and it has
been adopted widely enough that a large ecosystem of BIDS Apps can consume
any conforming dataset without bespoke glue code.

That design succeeds because it is deliberately minimal about
\emph{content}. BIDS says a great deal about where a file goes and how it is
named, and comparatively little about what the numbers inside a behavioral
table actually mean. For imaging this is the right trade-off, since
acquisition parameters are already standardized by the scanner and DICOM
conversion. For questionnaires and other behavioral measures it leaves the
scientifically decisive part unspecified: the exact wording of an item, the
labels attached to each response level, which items are reverse-scored,
which version or language of an instrument was administered, and how a
published subscale score is computed from raw items. BIDS provides
\texttt{phenotype/} tables for participant-level measures, but these are
flat aggregates and cannot by themselves carry session-, run-, and
variant-resolved administration context.

\subsection{The resulting gap}

Reproducible psychology requires more than stable filenames. Researchers
need machine-readable descriptions of survey items, response options,
reverse coding, units, acquisition settings, participant variables, and
instrument versions. In practice, these details are often scattered across
spreadsheets, survey platform exports, protocol documents, and manuscript
drafts. This creates ambiguity during reanalysis, cross-study comparison,
and long-term reuse.

The gap becomes especially visible in mixed-modality studies. A
BIDS-formatted imaging dataset may be structurally correct while still
lacking the metadata needed to interpret repeated questionnaire
administrations, compare two versions of the same instrument, harmonize
participant variables, or regenerate derived scores. These problems are not
only about validation; they are also about conversion, template reuse, and
keeping metadata synchronized with the data that produced it.

Two further observations shaped PRISM's design. First, behavioral research
is open-ended in a way imaging is not: there is no finite, enumerable list
of psychological instruments, and any schema that tries to enumerate them
is obsolete on arrival. A usable standard for this domain has to constrain
the \emph{shape} of a description without fixing its \emph{vocabulary}.
Second, a standard is only adopted if the path of least resistance leads to
compliance. BIDS gives a structure; it does not give a researcher holding a
LimeSurvey export and a spreadsheet codebook any help getting there. We
therefore treat validation and user experience as first-class parts of the
contribution rather than packaging around it.

PRISM addresses this need by providing a single workflow layer for
psychology-oriented metadata on top of BIDS. It offers schema-based
validation for additional modalities, converters from common tabular and
survey exports, reusable instrument templates, recipe-based scoring,
participants.tsv generation, and manuscript-facing outputs such as methods
boilerplate. The intended users are researchers, data stewards, and tool
developers who want richer guarantees for behavioral metadata without
giving up compatibility with established BIDS tooling.

\section{State of the field}

PRISM complements rather than replaces established tools in the BIDS
ecosystem. The official BIDS Validator and the broader BIDS standard are
essential for core structural compliance, especially for imaging data
\citep{gorgolewski2016bids}. BIDS \texttt{phenotype/} tables offer a useful
flat representation of participant-level measurements, but they cannot
retain all session, run, and acquisition-variant context for repeated
instrument administrations. PRISM therefore uses subject-, session-, and
run-resolved survey files as its native representation, while providing an
optional, deliberately lossy \texttt{phenotype/} bridge for compatibility
with existing BIDS workflows. PRISM adds checks for item-level metadata,
recipe-based scoring rules, and project-facing conversion workflows that the
BIDS Validator does not attempt to enforce. DataLad is highly effective for
dataset versioning, provenance, distribution, and nested dataset management
\citep{halchenko2021datalad}, but it is not designed to define domain
schemas for psychological instruments or to normalize questionnaire exports
into BIDS-compatible tabular layouts.

Survey collection platforms such as LimeSurvey solve a different problem
again: they help author and administer instruments, but they do not by
themselves produce a reusable research dataset with BIDS-style naming,
sidecars, schema validation, participants harmonization, and derivative
generation. PRISM was therefore developed as a separate toolkit because the
scholarly contribution lies in integrating these concerns: additive BIDS
compatibility, psychology-oriented schemas, template libraries, conversion,
scoring, and export in one reproducible workflow. Contributing isolated
pieces of this functionality upstream would not by itself provide the
end-to-end workflow needed by the target users.

A second distinction concerns how each approach handles the open-endedness
of behavioral measurement. Instrument-specific converters and curated
questionnaire databases solve the problem by enumeration: they support the
instruments someone has already encoded, and an unsupported questionnaire
requires either a code contribution or a wait. PRISM instead fixes the
description contract and leaves the vocabulary open
(Section~\ref{sec:openended}), so an unfamiliar, translated, or newly
devised instrument is a data-authoring task for the researcher who has it
rather than a feature request addressed to us. The bundled library is then a
starting convenience rather than the boundary of what the system can
express.

\section{Software design}

\subsection{An open-ended schema layer, not a closed specification}
\label{sec:openended}

The central design decision is that PRISM's schemas constrain the shape of a
description without enumerating its vocabulary. A survey template's item
namespace is deliberately not fixed: the schema declares that \emph{any}
item identifier is acceptable provided the object behind it satisfies an
item contract (a human-readable \texttt{Description}, optional
\texttt{Levels} mapping values to labels, \texttt{MinValue}/\texttt{MaxValue}
bounds, \texttt{DataType}, \texttt{Unit}, \texttt{AllowedValues}, and so on).
A lab can therefore describe an instrument PRISM has never seen, in a
language PRISM does not ship, and still obtain full machine validation of
that description. Nothing has to be added to PRISM first. This is what we
mean by building \emph{on} BIDS while staying open-ended: the structural
contract is fixed and checkable, the scientific vocabulary is not.

Several mechanisms extend the same principle across the system:

\begin{itemize}
  \item \textbf{Instruments evolve, and the schema follows.} Items carry
  \texttt{ApplicableVersions} so a single template can describe both the
  short and long form of an instrument; \texttt{VariantScales} let the same
  question carry a different response format per variant (for example a
  five-point Likert scale in one variant and a 0--100 visual analogue scale
  in another); and \texttt{Aliases}/\texttt{AliasOf} reconcile the same
  question appearing under different identifiers across studies, without
  editing the source data.

  \item \textbf{Validation strictness is a profile, not a constant.} The
  schemas carry an \texttt{x-prism} extension block declaring which fields
  are required only for the curated official library
  (\texttt{officialOnlyRequired}) and which only for real project data
  (\texttt{projectOnlyRequired}). One schema therefore enforces
  curation-grade completeness on the bundled library while remaining
  permissive enough that a researcher's own in-progress questionnaire is not
  rejected for lacking a citation.

  \item \textbf{Schema versions coexist.} Three schema versions
  (\texttt{stable}, \texttt{v0.1}, \texttt{v0.2}) ship side by side and are
  selectable per run with \texttt{--schema-version}, so a dataset validated
  in 2025 can still be validated against the rules it was authored under.

  \item \textbf{Users can add their own checks.} The validator loads custom
  validator plugins from a \texttt{validators/} directory inside the dataset
  or from a \texttt{plugins} array in the project's
  \texttt{.prismrc.json}; \texttt{prism-validator --init-plugin <name>}
  scaffolds one. Site-specific or study-specific rules (a local
  participant-ID convention, a consortium requirement) become enforceable
  without patching PRISM.

  \item \textbf{Context enrichment is modular and opt-in.} Sessions can be
  annotated with acquisition-time environmental context through independent
  provider modules (weather, air quality, pollen), enabled per run with
  \texttt{--environment-providers} and cached locally. This is the one part
  of PRISM that contacts an external service (see
  Section~\ref{sec:ux}); it is off by default and never required to produce
  a valid dataset.
\end{itemize}

Twelve object and modality schemas currently ship in the \texttt{stable}
version, covering surveys, biometrics, physiological recordings, eye
tracking, events, environment/context, entities, recipes, projects, dataset
descriptions, the instrument registry, and LimeSurvey import.

\subsection{Additive BIDS compatibility}

PRISM-specific files live alongside standard BIDS content, and
\texttt{.bidsignore} support allows standard BIDS tools to ignore PRISM-only
artifacts when necessary. This makes it possible to retain acquisition
context in native survey files while keeping BIDS apps usable. PRISM never
requires a dataset to stop being a BIDS dataset.

\subsection{Metadata as an executable contract}

Survey and biometrics templates separate instrument identity and item
definitions from study-specific administration details. Versioned JSON
schemas, a registry of instrument identifiers and citations, and declarative
entity rules provide one machine-readable basis for conversion, filename
construction, and validation. This supports multilingual templates,
instrument variants, and version-aware scoring without requiring researchers
to reconstruct those decisions from spreadsheet conventions. Most bundled
survey templates are derived from the PsyToolkit survey library
\citep{stoet2010psytoolkit,stoet2017psytoolkit}; each template's metadata
records the upstream licensing statement verbatim, and instruments with
unclear or restrictive terms are excluded rather than shipped (103 survey
and one biometrics template at the time of writing). The bundled library is
a convenience, not a constraint: it is an ordinary set of templates using
exactly the same open item contract described in
Section~\ref{sec:openended}, and a project may ignore it entirely or point
PRISM at its own library.

\subsection{Auditable derived data and sharing decisions}

Recipe outputs include derivative metadata and per-recipe provenance
sidecars recording the recipe identifier and version, PRISM version,
timestamp, and SHA-256 hashes of input files. DataLad support is optional,
but records scoped changes when used. The sharing workflow validates
selected content before export and can randomize participant identifiers,
mask copyrighted question text, scrub sensitive MRI sidecar fields, or apply
anatomical defacing to the export copy. It prepares reusable project
templates, analysis-oriented exports, and repository packages such as
Austrian NeuroCloud submissions; optional openMINDS metadata export supports
semantic sharing.

\section{The validator}
\label{sec:validator}

The validator is the component everything else is organized around. A schema
that is not mechanically enforced is documentation, and documentation
drifts. Making the metadata contract executable is what turns PRISM's
templates from a convention into a guarantee, so the validator is designed
to be usable in every setting where that guarantee matters: interactively
while authoring, at the command line before sharing, and unattended in
continuous integration.

\textbf{Two independent layers.} \texttt{prism-validator} runs PRISM's own
schema and consistency checks, and with \texttt{--bids} additionally invokes
the official BIDS Validator over the same tree, merging both result sets
into one report. The layers are deliberately not merged in implementation:
PRISM never reimplements or second-guesses BIDS structural rules, so a
dataset that passes remains valid by the upstream standard's own definition,
and users are never asked to trust our reading of the specification.
Section~\ref{sec:validation} demonstrates both layers firing on the same
dataset.

\textbf{Machine-readable output for automation.} Reports are emitted as
JSON, SARIF, JUnit, Markdown, or CSV. SARIF surfaces findings as code-scanning
annotations, and JUnit lets a dataset be checked by the same CI machinery
that runs a test suite. The validator is distributed as a standalone
executable, a lightweight Docker image, and a GitHub Action, so validating a
dataset on every push requires no local installation. In effect a dataset
can be placed under the same regression discipline as software.

\textbf{Repair, previewed before it is applied.} A subset of findings is
auto-fixable: creating a \texttt{dataset\_description.json} template,
generating missing sidecar stubs, updating \texttt{.bidsignore} for PRISM
compatibility, and creating an optional \texttt{.prismrc.json}.
\texttt{--list-fixes} enumerates them, \texttt{--dry-run} prints exactly
what would change, and only \texttt{--fix} writes. The design rule is that
the tool never silently modifies a researcher's data; a destructive or
lossy step is always previewable first.

\textbf{Validating the description, not only the data.} Because templates
are themselves schema-governed artifacts,
\texttt{--validate-templates <path>} checks an instrument library before it
is ever used to convert anything, catching a malformed codebook at
authoring time rather than after it has been applied to a hundred
participants.

\textbf{Reproducible and extensible.} Validation is pinned with
\texttt{--schema-version}, so a result is reproducible against the rules the
dataset was authored under, and extended with custom plugins
(Section~\ref{sec:openended}) so local conventions are enforced by the same
command that enforces the standard ones.

\section{Helper functions for the unglamorous work}
\label{sec:helpers}

Between a raw export and a valid dataset lies a long tail of mundane,
error-prone data wrangling that standards documents do not address and that
researchers otherwise solve with disposable scripts. PRISM ships this work
as fourteen documented command groups under \texttt{prism\_tools}, each
available both in Studio and as a scriptable CLI subcommand:
\texttt{convert}, \texttt{wide-to-long}, \texttt{participants},
\texttt{environment}, \texttt{survey}, \texttt{biometrics},
\texttt{physio}, \texttt{recipes}, \texttt{dataset}, \texttt{anonymize},
\texttt{template-export}, \texttt{library}, \texttt{file-management},
\texttt{json-editor}, and \texttt{demo}.

Representative examples show the intended level of abstraction.
\texttt{wide-to-long} reshapes a spreadsheet whose column names encode
session (a near-universal shape for longitudinal questionnaire exports) into
the long format PRISM stores, rather than leaving the researcher to write
the pivot by hand. \texttt{participants} detects which column holds the
participant identifier, previews the normalization, and only then writes
\texttt{participants.tsv}. \texttt{anonymize} randomizes participant
identifiers and masks copyrighted item text in an export copy.
\texttt{template-export} produces a reusable project skeleton with subject
data stripped, so a validated study design can seed the next study.
\texttt{recipes} recomputes derived scores from raw items with provenance
attached, making a published subscale reproducible from the deposited data
rather than from a description in a methods section.

Individually these are small. Collectively they are the difference between a
standard that is theoretically satisfiable and one that a lab actually
satisfies on a deadline.

\section{User experience as a design goal}
\label{sec:ux}

BIDS defines a structure; it does not make that structure easy to reach.
We treat the resulting last-mile problem as a legitimate research-software
contribution rather than as cosmetics, because a correctness guarantee that
is too costly to obtain is not obtained. The typical entry point is not a
clean slate but a LimeSurvey archive, an Excel codebook of uncertain
provenance, and a folder of scanner output, held by a researcher whose
expertise is psychology rather than data engineering.

PRISM Studio is a local-first web application: it runs on the researcher's
own machine, and participant data is neither uploaded nor sent to a remote
service. The single exception is the optional environment-enrichment feature,
which queries a public weather and air-quality service with coordinates and
dates in order to annotate sessions with acquisition-time context; it is
disabled by default, and no participant-level data is transmitted. Studio
presents around twenty task-oriented screens, including six guided
converters, a template editor, a survey generator and customizer, a recipe
builder, a JSON sidecar editor, a file-management view, and a share/export
wizard. Three conventions run through them.

\textbf{Guidance where the domain knowledge is needed.} Converters ask
domain questions (which column identifies the participant, which session
this file belongs to) instead of demanding that the user pre-arrange files
into a layout they must first learn. The correct BIDS names are then derived
from the declarative entity rules rather than typed by hand, which removes
an entire class of naming errors at the source.

\textbf{Preview before commit.} Conversions, participant-ID normalization,
entity renames, validator fixes, and exports all offer a preview of what
will change. Operations that could collide or lose data report the conflict
instead of resolving it silently, a property exercised directly by the
adversarial cases in Section~\ref{sec:validation}.

\textbf{Parity between the interface and the command line.} Every Studio
action is reachable from the CLI, so exploratory interactive work and
automated reproducible pipelines are the same operations rather than
divergent implementations. A lab can start in the interface and graduate to
scripting without rewriting its workflow, and results obtained either way
are identical.

\section{Validation evidence}
\label{sec:validation}

A recurring weakness in software papers is asserting correctness without
demonstrating it. PRISM's test suite includes a deterministic, seeded
adversarial dataset generator (\texttt{prism\_tools dataset
build-hostile-demo}) that is entirely synthetic: no real participant data is
used or required. Given a fixed random seed, it constructs 59 deliberately
hostile cases across nine pipeline domains --- sociodemographics,
biometrics, environment/MRI sidecar timestamps, subject and session
identifiers, BIDS entity rewriting, recipe/scoring definitions,
input-format diversity (character encodings, spreadsheet formula-like
strings), full survey conversion runs, and participants-table merging.
Each case documents an expected pipeline outcome, for example:

\begin{itemize}
  \item three participants use session labels \texttt{ses-1},
  \texttt{ses-01}, and \texttt{ses-pre} for the same subject, which must
  remain three distinct, uncoerced session labels through every pipeline
  stage rather than being treated as equivalent;
  \item a subject directory named with a non-ASCII character
  (\texttt{sub-M\"uller}) must be handled without the pipeline crashing;
  \item conflicting recipe definitions (an unresolvable formula reference, an
  invalid \texttt{Kind}, a missing required field) must be rejected by
  recipe validation with a clear error rather than silently producing a
  wrong score;
  \item malformed or ambiguous MRI sidecar timestamps (an invalid calendar
  date, a Daylight Saving Time transition, a non-existent leap day) must
  fail to parse cleanly rather than raising an unhandled exception.
\end{itemize}

Thirty-four automated tests assert these documented outcomes case-by-case
and run in continuous integration on every commit, so a regression in any of
the 59 cases is caught immediately rather than discovered by a user.

As an end-to-end illustration for this manuscript, we additionally built the
full synthetic dataset from the same seed and ran both PRISM's own validator
and the official BIDS Validator against the resulting project
(\texttt{prism-validator examples/hostile\_demo --bids}), reproducible with
one command. Table~\ref{tab:validation} reports the result.

\section{FAIR-oriented dataset preparation}

PRISM supports FAIR-oriented dataset preparation \citep{wilkinson2016fair},
but does not make a dataset FAIR automatically. Findability is supported by
BIDS-style names, versioned schemas, instrument identifiers, keywords, and
DOI/citation fields. Standard JSON, TSV, and CSV formats, BIDS alignment,
optional \texttt{phenotype/} and openMINDS exports, licensing metadata, and
recipe provenance support accessibility, interoperability, and reuse. Actual
access conditions, consent, licensing, and repository deposition remain the
responsibility of the dataset owners.

\section{Research impact statement}
\label{sec:impact}

PRISM has supported a research-data workflow for the Austrian NeuroCloud
dataset \emph{Creativity: a (white) matter of connectivity}
\citep{koschutnig2026creativity}. Its public metadata record identifies
PRISM Studio version 1.15.2 as the creation tool; the authors used PRISM to
enrich the mixed-modality BIDS dataset with metadata and validate it before
repository submission. This is documented author/developer use rather than
evidence of independent adoption, and the dataset remains access-restricted
under the Austrian NeuroCloud data-use agreement.

The public repository shows iterative development from September 2025
onward, tagged releases through version 1.18.0, automated continuous
integration, and cross-platform release artifacts for macOS, Windows, and
Linux. The repository also includes workshop materials, example datasets
(including the synthetic adversarial dataset described in
Section~\ref{sec:validation}), and end-to-end documentation so that
researchers can test the workflows locally rather than treating the software
as an opaque web service.

The scientific value of PRISM is its attempt to make structured behavioral
metadata operational in day-to-day research practice. The bundled template
library, participants and NeuroBagel workflows, survey version handling,
wide-to-long reshaping, LimeSurvey integration, and repository-facing
exports reduce the amount of manual metadata reconciliation required to move
from raw collection outputs to reusable datasets. This is particularly
relevant for labs that already use BIDS for imaging data but still manage
questionnaires and participant metadata in less standardized ways.

\section{Availability and reproducibility}

PRISM is released under the GNU Affero General Public License v3.0
(AGPL-3.0) and developed at
\url{https://github.com/MRI-Lab-Graz/prism-studio}. The release described
here is version 1.18.0. Source installation is documented for macOS,
Windows, and Linux through \texttt{setup.sh} and \texttt{setup.ps1}; entry
points include \texttt{python prism-studio.py} for the web application and
\texttt{prism-validator} for portable validation. The validator is also
distributed as platform bundles, a Docker image, and a GitHub Action. The
repository contains example datasets and workshop material under
\texttt{examples/}, while automated checks are run in CI through
\texttt{python tests/verify\_repo.py} and pytest-based verification. The
bundled instrument library is third-party content rather than PRISM's own
code and is licensed separately; see the library's own notice for
provenance and per-instrument terms.
